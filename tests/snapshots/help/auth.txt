
 Usage: wp-bulk auth [OPTIONS] [COMMAND] [ARGS]...

 Доступы: отчёт об их здоровье и хранение доступов сайтов в OS keychain.

 Откуда wp-bulk берёт домен, логин и пароль сайта. Первый источник, где поле есть, выигрывает — для
 каждого поля отдельно:

 1. Флаги команды: --domain / --username / --password (где они есть).

 2. Окружение процесса. Домен: WP_DOMAIN. Логин: WP_<SLUG>_API_USER, WP_API_USER. Пароль
 приложения: WP_<SLUG>_API_TOKEN, WP_API_TOKEN. Сначала имя сайта, затем общее. <SLUG> — домен
 заглавными, всё кроме букв и цифр заменено на «_» (example.com → WP_EXAMPLE_COM_API_USER).
 Запасные имена antagor: SITE_DOMAIN, SITE_REST_API_USER, SITE_REST_API_PASSWORD; свои WP_*
 главнее, а при заданном SITE_CMS не равном wordpress алиасы отключены. SITE_PROD не читается
 никогда.

 3. OS keychain, запись wp:<домен>: `wp-bulk auth login --provider wp:<домен>`.

 4. .env проекта (legacy, последним): ищется от текущей папки вверх или берётся из --project. Имена
 те же (WP_DOMAIN, WP_API_USER, WP_API_TOKEN и алиасы antagor).

 Doppler. wp-bulk сам не читает Doppler, Windmill и любое другое хранилище секретов. Хранилище
 кладёт значения в окружение под именами выше — это делает вызывающий. В Doppler имена несут
 префикс сайта (TZM_SITE_REST_API_PASSWORD): wp-bulk префикс не отрезает, вызывающий
 переименовывает сам:


   doppler run --project projects --config prd -- sh -c '
     export WP_DOMAIN=tzm.example.com
     export WP_API_USER="$TZM_SITE_REST_API_USER"
     export WP_API_TOKEN="$TZM_SITE_REST_API_PASSWORD"
     wp-bulk fetch ...'

 Что используется на деле: `wp-bulk auth status --json` — источник каждого поля
 (cli/env/keychain/.env), без значений; --check проверяет доступ одним read-only запросом.

 Доступов нет — не ошибка для команд только на чтение (работают анонимно); для записи нужны.
