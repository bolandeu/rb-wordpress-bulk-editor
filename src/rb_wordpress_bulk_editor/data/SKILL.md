# wp-bulk — соглашения для агента

CLI синхронизации WordPress ↔ данные проекта (Excel или JSON).

Здесь только соглашения. **Список команд здесь не дублируется**: его печатает
голый `wp-bulk` (имя, версия, описание и первая строка docstring каждой команды),
а подробности — `wp-bulk <команда> --help`, где указаны и exit-коды.

## Установка

```bash
uv tool install "git+https://github.com/bolandeu/worppress-bulk-editor.git"
uv tool upgrade rb-wordpress-bulk-editor
```

Дистрибутив называется `rb-wordpress-bulk-editor` (раньше — `wp-bulk-editor`),
команда — `wp-bulk`. Со старым именем сначала удалить его, иначе два
инструмента спорят за одну команду: `uv tool uninstall wp-bulk-editor`.

Репозиторий приватный: `uv tool install` ходит через git, авторизация — та же,
что у `git clone` (credential helper после `gh auth login`, либо форма
`git+ssh://git@github.com/bolandeu/worppress-bulk-editor.git`).

## Вывод

- `--json` — машиночитаемый конверт; **stdout только данные**.
  Успех: `{"ok": true, ...поля команды, "cli_version"}`.
  Ошибка: `{"ok": false, "error": {"code", "message", "action"?}, "cli_version"}` — тоже в stdout.
  `cli_version` — версия пакета, которым сделан результат (null при запуске из исходников).
- Без `--json` — человеческий вывод в stdout, диагностика и ошибки в stderr.
- `--quiet` — только существенное, `--verbose` — подробная диагностика (stderr).
- Флаги `--json/--quiet/--verbose/--non-interactive` работают и до команды
  (`wp-bulk --json doctor`), и после (`wp-bulk doctor --json`).

## Exit-коды

| код | значение |
| --- | --- |
| 0 | успех |
| 1 | общая ошибка (`UNEXPECTED`, `ABORTED`, `CREDENTIAL_STORE_UNAVAILABLE`) |
| 2 | неверные аргументы (`INVALID_ARGUMENTS`) |
| 3 | нужны credentials (`AUTH_REQUIRED`) или доступ неисправен (`CREDENTIALS_UNHEALTHY`, `auth status`) |
| 4 | проект не инициализирован (`PROJECT_NOT_INITIALIZED`) |
| 5 | ошибка внешнего сервиса (`PROVIDER_ERROR`: сеть, таймаут, 5xx, 429) |
| 6 | CLI старее, чем требует проект (`CLI_TOO_OLD`) |

## Credentials

Порядок разрешения: **CLI-флаг → переменная окружения → OS keychain**
(`.env` проекта — legacy-слой, устаревший и только для существующих проектов).
Секреты никогда не пишутся в файлы проекта.

Переменные: общие `WP_DOMAIN`, `WP_API_USER`, `WP_API_TOKEN`; для конкретного
сайта — `WP_<DOMAIN>_API_USER` / `WP_<DOMAIN>_API_TOKEN` (домен в верхнем
регистре, не-буквенно-цифровые символы → `_`: `example.com` → `WP_EXAMPLE_COM_API_USER`).
В keychain credential хранится по домену сайта — у каждого сайта свой логин:
`wp-bulk auth login --provider wp:<домен>` (пароль — из окружения или скрытым
вводом), `wp-bulk auth logout --provider wp:<домен>`.

`.env` проекта antagor тоже понимается без переименования: `SITE_DOMAIN`,
`SITE_REST_API_USER`, `SITE_REST_API_PASSWORD` — запасные имена для `WP_DOMAIN`,
`WP_API_USER`, `WP_API_TOKEN` (свои имена главнее). Учитываются, только если
`SITE_CMS` не задан или равен `wordpress`.

Здоровье доступов: `wp-bulk auth status [--check] --json` — общая форма отчёта
всех наших CLI (запись `wp:<домен>` на каждый сохранённый сайт и сайт проекта;
значения не печатаются). Exit 3 и
`CREDENTIALS_UNHEALTHY` — обязательный доступ не в порядке или любой неверен.

Проверить готовность окружения: `wp-bulk doctor --json`
(credentials и их источник, проект, конфиг, совместимость версии;
`--check-connection` добавляет реальный запрос к сайту).

## Безопасность: опасные операции

Общий гейт для всего необратимого:

1. `--dry-run` показывает план и ничего не делает — вопросов не задаёт;
2. дальше требуется подтверждение: человеку задаётся вопрос, а под
   `--non-interactive` (и в `--json`, и когда stdin не терминал) команда без
   `--confirm` падает с `INVALID_ARGUMENTS` (exit 2).

Что именно гейтится:

- **`bulk-delete`** — удаляет записи целыми типами; с `--force` мимо корзины.
- **`sync` / `async`** — сами по себе обратимы (перезапуск даёт тот же
  результат, контент удаляется в корзину), **кроме двух путей**: строки листа
  `media` с `action=delete` и флаг `--delete-media` — вложения и featured-
  изображения удаляются **навсегда**, мимо корзины. Подтверждение спрашивается
  только когда такой путь реально задействован в этом прогоне.
- **`options`** без `--fetch` — перезаписывает настройки живого сайта,
  прежние значения нигде не сохраняются. `options --fetch` и `fetch-media` —
  пересборка непустого таба `options` / `media` в файле (JSON или xlsx).
- **`fetch`** без `--file` — перезапись существующего `fetch.xlsx`.

Перед любым неинтерактивным запуском с `--confirm` **спроси явное согласие
пользователя** — как спросил бы человек. Сначала `--dry-run`.

## Проект

`--project <name>` подключает каталог проекта: его `.env`, данные, `media/`,
`content/`, `logs/`. Приоритет: CLI-флаги > `.env` проекта > глобальный `.env`.

Проект может объявить минимальную версию CLI: `WP_BULK_MIN_VERSION=1.2.0`
в своём `.env`. Более старый установленный CLI падает с `CLI_TOO_OLD` (exit 6),
`doctor` показывает это проверкой `cli_compat`.

## Данные: два независимых источника

Источник выбирается по расширению файла данных, объединения источников нет.

- **Excel (`.xlsx`)** — листы = наборы записей, имя листа задаёт тип записи.
- **JSON (`.json`)** — словарь именованных наборов («вкладок»), каждый набор —
  массив записей-словарей. Тип записи задаёт сама запись: `type` — тип контента
  (имя записи в `title`), `taxonomy` — термин таксономии (имя в `name`);
  поля взаимоисключающие. Наборы `options` (`{key, value}`) / `media` —
  служебные: их читают и пишут `options` и `fetch-media`, не `sync`.

Оба направления работают с JSON: `sync`/`async` (файл → сайт), `update`
(поля с сайта по id), `fetch --file *.json` (сайт → один таб на сайт, таб
пересобирается целиком), `validate` (проверка файла без сайта). Для всех —
`--sheets` с именами табов обязателен, кроме `fetch`. `fetch` не пишет в
реестр `<проект>/<проект>.json`.

Остальные поля одинаковы для обоих источников: `action`, `id`, `slug`,
`status`, dot-нотация `seo.*` / `acf.*`, поля таксономий по имени таксономии.

**Проверка перед отправкой.** `sync`/`async` сначала проверяют данные (то же
показывает `validate`) и при ошибках останавливаются с exit 2 до первого
изменения на сайте, в том числе при `--dry-run`: неизвестные имена полей
(кроме `acf.*`, `acf_*`, `meta.*`; с подсказкой похожего); таксономии и типы —
по сайту: колонка-таксономия есть на сайте и привязана к типу записи, `type` /
`taxonomy` записей существуют; `id` у update/delete, `status`, дубли `slug`,
`;` без пробела в терминах, отсутствующие файлы. Своё поле проекта — в
`WP_EXTRA_FIELDS` (`.env`), а не `--skip-checks`: этот флаг отключает проверку
целиком. `validate` без доступов к сайту (или с `--offline`) проверяет без
сайта и отвечает `site_checked: false`.

**Прогресс.** По завершении каждой записи `sync`/`async` пишут в лог строку
`[17/104] id=3425 updated` (итог: `added`/`updated`/`deleted`/`error`; под
`--json` лог в stderr). В `async` номер — доля сделанного, не позиция в файле.

**Загрузка медиа** (`media-upload`) с файлом данных не работает: получает пути,
отдаёт id вложений (`uploaded`/`failed`, `path` — дословно как передан).
Частичный успех — `ok: true` и exit 0; ошибка только если не загрузилось ничего.

`action` (регистр не важен): `add`/`a`; `update`/`u`/`edit`/`e`;
`delete`/`d`; `skip`/`s`/`0`. Пусто или другое значение — запись пропускается.

**Дата публикации.** Заполненное `date` при `add`/`update` уходит в WordPress
(время сайта): `2026-01-12T17:16:41`, `2026-01-12 17:16`, `12.01.2026`;
нераспознанное — ошибка проверки. Будущая дата у `publish` — запись станет
запланированной. `modified` только читается: его ставит сам сайт при сохранении.

**Значение-путь → содержимое файла.** Если значение поля — путь, оканчивающийся
на `.html`/`.htm`/`.md`/`.markdown`/`.txt` (без `://`), в WordPress уходит
содержимое файла (markdown → HTML): `"acf.more": "content-write/3425.html"`.
Относительный путь — от папки файла данных (выйти за неё через `..` нельзя),
абсолютный — как есть. Файла нет — ошибка записи, путь строкой не отправляется.
Не применяется к `title`, `name`, `slug`, `custom_permalink`, `link`, `status`, `password`.

## Таксономии

- Таксономии берутся с сайта при каждом прогоне — вписывать их в `.env` не
  нужно. Без сайта (`validate --offline`) поле считается таксономией, если
  его имя есть в `WP_TAXONOMIES`, объявлено в файле записями-терминами или
  листом, входит в стандартный набор (`category`/`tag`) или
  имя разбито `_`/`-` на части, и одна из частей — `cat` / `tax` / `term` / `tag` (`rb_services_cat`, `cat_services`, `region-term`; не `catalog_url`). Имя — строчными.
- Несколько терминов в одном поле разделяются `"; "` (точка с запятой + пробел).
- Внутри одного термина иерархия задаётся `>`: `"термин1; термин2>термин2.1"` —
  предки создаются слева направо, записи присваивается последний уровень.
  `>` только для иерархических таксономий: если WP проигнорировал `parent`,
  будет ошибка валидации, а не тихие дубликаты.
- **Первый термин строки — основной (primary)**, пишется в мету Yoast
  `_yoast_wpseo_primary_<taxonomy>` best-effort: ошибка этой записи не валит
  синхронизацию.
